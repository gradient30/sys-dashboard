## 1. P0-1 内存清理兜底路径 100% 崩溃（HTTP 层必然失败）

| 项 | 内容 |
| --- | --- |
| 位置 | `memclean_svc.py:398-408`（`do_POST` 的 `/cleanup/<token>` 分支） |
| 复现 | `curl -X POST http://127.0.0.1:61210/cleanup/Glc-2026-mc-7f3a91` → `curl: (52) Empty reply from server` |
| 实测 traceback | `UnboundLocalError: cannot access local variable 'e'`，抛点 `memclean_svc.py:408` |

### 根因

```python
except Exception as e:
    # ② 兜底：本地 EmptyWorkingSet 方案
    pass                      # ← except 块结束，CPython 自动 del e
...
f.write(f"... [fallback:{str(e)[:40]}] ...")   # ← 引用已删除的 e
```

`except ... as e` 的目标名在 except 块结束时被 `del`，块外再引用即 `UnboundLocalError`。
**这不是偶发，是结构性必现**——只要走兜底分支就 100% 触发。

### 为何长期未被发现

`web/index.html:1019` 的前端兜底把 `TypeError`/网络类错误一律改报「🧹 清理已在后台执行」
并置 `cleanLast = Date.now()`。**UI 显示成功，HTTP 层实际是断连/500。**
前端兜底掩盖了后端崩溃，这是本条最值得记取之处。

### 影响边界

- 崩溃发生在 `do_cleanup()` **之后** → EmptyWorkingSet 修剪**实际已执行**
- 但 `self._json(200, out)` **未执行** → 前端拿不到 `freed_gib`/`before_gib`/`after_gib`
- **日志未落盘**：`%TEMP%\memclean_svc.log` 实测 **0 字节** → 事后**无审计痕迹**
- **当前必然走兜底**：`schtasks /query /tn MemReduct-Clean` → `ERROR: The system cannot find the file specified`，
  与 `CLAUDE.md:38` 记载的"任务未注册"一致 → **每次点按钮都命中此路径**

### 需人工判定

1. `memclean_svc.log` 0 字节是否意味着**从未有过一次成功的兜底清理**？
   若是，则 `docs/REQUIREMENTS.md:26` 与 `docs/RUNBOOK.md` 中
   "按钮实际走 EmptyWorkingSet fallback（本地方案，可用但释放量较小）" 的表述**不准确**——
   现状是"fallback 每次都崩"。
2. `docs/TECH.md:42-43` 的排障步骤（"查计划任务…当前未注册，按钮走 fallback 属现状非故障"）
   会把人引向错误方向，需同步修正。

## 2. P0-2 兜底分支"吞异常 + 跨块引用变量"属结构性反模式

与 P0-1 同源，但**独立成条**——它反映的是一类模式问题，而非单点笔误。

- `memclean_svc.py:398` 的 `except Exception as e: pass` **吞掉了异常且丢弃了 `e`**，
  却在 10 行之后引用它
- 异常被 `pass` 吞掉 → 无任何告警 → 只有后续的 `UnboundLocalError` 暴露问题
- 若当时**没有**第 408 行的日志写入，异常会被**完全静默吞掉**，用户以为清理成功

**建议审核点**：确认是否需要在兜底分支保留异常信息，用于前端提示
"已降级为本地方案，原因：xxx"，而非静默。

## 4. P1-2 `cpu` 仍写入 `0.0`，净化规则有漏网

```
cpu NULL: 3223        ← 已正确置 NULL
cpu == 0.0: 21        ← 疑似坏帧被当 0 写入
cpu == 100.0: 10      ← 满载帧（正常）
```

`memclean_svc.py:234` 的净化判据为 `total == 0 and idle == 0` → 置 NULL。
`docs/TECH.md:104-112`（坑 8）称已做"三处守卫"。

**但仍残留 21 行 `cpu=0.0`**。推断：存在 `total == 0` 而 `idle != 0` 的帧——
按数学 `total=0 ⇒ idle=100`，这类帧 `total` 为 0 但 `idle=100`，**不满足当前判据**
（判据要求 idle 也为 0），于是 `round(0, 2)` → 写入 `0.0`。

**需人工判定**：`cpu=0.0` 这 21 行是"真 0%"还是"坏帧"？
建议人工核对该 21 行的时间戳与同期负载是否吻合。
**这与坑 8 声称的"零误杀"结论有张力**，判据需复核。
